Module 4.1 ~35 min with hands-on practice

A website that’s easy to understand

Organize pages, identity, and evidence so people and systems can find clear information.

0 of 0 0%

What is
A page needs to present its topic clearly.

Why learn
Working with observable changes avoids measuring success only by a tool score. You improve the site’s usefulness and record what was actually fixed.

Key concepts
Discovery · Understanding · GEO · Evidence

What is
If several services appear only on a single page without specific links, it’s hard to point to a particular item.

Why learn
A specific address makes it easier to look up, reference, and maintain. It also reduces ambiguity when someone shares only one catalog service.

Key concepts
URL · Anchor · Specificity · Usefulness

What is
Name, description, and contacts must represent the same organization.

Why learn
Consistency helps people understand who provides the content and how to get in touch. It prevents contradictions introduced by templates and copied pages.

Key concepts
Identity · Consistency · Relationship · Structured data

What is
Technical statements, numbers, and comparisons need appropriate support.

Why learn
The reader needs to be able to distinguish description, evidence, and hypothesis. This clarity helps evaluate trust and reduces the chance that a promotional sentence turns into an improper promise.

Key concepts
Support · Method · Limitation · Example

What is
A report should point to page, problem, impact, and the smallest correction.

Why learn
Small tasks make the audit actionable. Repeating the same test connects recommendation and outcome without relying on a subjective evaluation afterward.

Key concepts
Finding · Impact · Correction · Retest

What is
Choose an exercise site or one of your own projects and select five pages.

Why learn
Practice prepares the delivery of a useful audit. It also shows that good structure and consistent information can be verified before any publication.

Key concepts
Sample · Inventory · Priority · Verification

Module 4.2 ~35 min with hands-on practice

Project: request hub

Combine scope, documents, interface, and review into a small local tool.

0 of 0 0%

What is
The center receives a CSV with identifier, client, task, and deadline.

Why learn
The contract combines the initial learnings and prevents the project from growing before it works. It defines a delivery that can be demonstrated with a few files.

Key concepts
MVP · Contract · Line · Conflict

What is
Create a file with complete orders, a missing deadline, a long name, and a repeated identifier.

Why learn
A varied set prevents the center from working only with the first row. The expected outcome serves as a reference during implementation and review.

Key concepts
Fixture · Extreme · CSV · Expected

What is
Represent import, validation, list, and export.

Why learn
Separating parts reduces coupling and makes review clearer. You can investigate a data rule without redoing the entire visual experience.

Key concepts
Import · Validation · Presentation · Export

What is
Ask the assistant to implement only the defined flow.

Why learn
Implementation gains a clear boundary and a definition of done. Opening the output in another tool checks whether the result is usable outside the original screen.

Key concepts
Implementation · Execution · Interoperability · Acceptance

What is
Test repeated import, an empty file, and invalid content.

Why learn
Tests bring the tool closer to real-world usage conditions. The review finds risks that don’t appear in the demonstration of a single successful path.

Key concepts
Repetition · Empty · Invalid · Limitation

What is
The final delivery brings together the tool, the fictitious data, the exported file, and a record of the checks.

Why learn
The project shows how several pills turn into a small tool. It also teaches how to deliver a result that someone else can verify and continue.

Key concepts
Demonstration · Evidence · Pending item · Delivery

Module 4.3 ~35 min with hands-on practice

Project: delivery and knowledge kit

Gather documentation, research, and verification so another person can continue the work.

0 of 0 0%

What is
A delivery needs to work for someone who didn’t follow the project conversations.

Why learn
The delivery quality determines the cost of continuing. A useful tool loses value when only its author knows how to start, test, or update it.

Key concepts
Recipient · Entry point · Autonomy · Limitation

What is
Separate code, examples, documentation, and evidence.

Why learn
Organization by function reduces search time and avoids mixing examples with real data. It also makes reviewing what will be published easier.

Key concepts
Code · Example · Documentation · Evidence

What is
List prerequisites, a start command, and a test action.

Why learn
An instruction is only validated once it’s been followed. This test reveals missing files, hidden dependencies, and path names that work only on the computer of the person who wrote it.

Key concepts
Prerequisite · Command · Result · Diagnosis

What is
Choose the documents that explain the project and record topic, version, and location.

Why learn
An organized base preserves decisions and reduces repeated questions. Version control prevents old answers from looking current just because they’re easy to find.

Key concepts
Index · Dependency · Update · Owner

What is
Before versioning, check the exact set of files.

Why learn
The review prevents distributing private material or an incomplete version. Identifying the delivery makes it possible to connect documentation, code, and test results.

Key concepts
Distribution · Tracked · Version · Published

What is
Assemble the order-central kit or another small project.

Why learn
This practice closes the course by connecting implementation and maintenance. You move from an AI-produced response to a delivery that can be checked, shared, and improved.

Key concepts
Second reader · Reproduction · Continuity · Conclusion
